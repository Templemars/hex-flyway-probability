# Meeting notes, 2026-04-11

## Main outcome

The session focused on tightening the transparency and interpretability of the H3 cost-component report before moving on to the first Dijkstra runs.

## Main technical updates

### 1. Diagnostic maps refined
The four component maps in the step-11 report were revised for better interpretability.

Current map design:
- parallel wind cost for straight northward flight
- crosswind cost for straight northward flight
- distance cost from the outgoing edge whose bearing is closest to north
- food cost from chlorophyll-a

Important interpretation:
- these maps are diagnostic visualizations
- the actual routing graph still uses true directed edges, true edge bearings, and true edge distances

### 2. Food-map pole issue diagnosed
A problem was identified in the food map near the poles.

Key finding:
- many polar cells are outside the common environmental support and have missing wind and chlorophyll values
- the old map risked visually mixing unsupported cells with real food-cost values

Decision for visualization:
- use the wind-data footprint as a common support mask for all four component maps
- treat this as a visualization decision, not automatically as a modeling exclusion rule

### 3. Shared color-scale decision refined
The first shared color scale used the raw maximum across the map layers, which compressed contrast.

Updated decision:
- use a shared color scale from `0` to the shared **P99** across the displayed standardized map layers
- keep the same scale across all four maps for comparability

Interpretation:
- this preserves comparability while avoiding a few extreme values flattening the visible structure in every map

### 4. Distance-map redesign
The earlier cumulative northward distance map was rejected as too artificial.

New diagnostic definition:
- assign to each source cell the true distance of the outgoing edge whose bearing is closest to north

Interpretation:
- this is still a diagnostic layer, not the routing distance term itself
- but it is now based on a real edge quantity rather than an artificial cumulative construction

### 5. Directional distance diagnostic added
A separate directional edge-distance summary was added to test whether the strange corridor-like patterns in the northward distance map reflect real graph anisotropy.

Outputs added:
- `results/tables/11_directional_edge_distance_summary.csv`
- `results/figures/11_directional_edge_distance_by_bearing.png`

Interpretation from first reading:
- the H3 graph does show modest directional variation in edge distances by bearing and latitude
- however, the visible corridor patterns in the northward distance map are stronger than the underlying anisotropy alone and are partly created by the map construction itself

### 6. Distance red flag recorded explicitly
A project red flag was added to keep the distance issue alive.

Current stance:
- the first true-edge-distance implementation turned out to be too harsh after direct P99 scaling, because most H3 neighbor distances cluster close to one another and therefore close to the upper standardized range
- the later extra-distance-above-median variant was also judged methodologically less clean than the paper logic
- the routing model should therefore return to the paper-consistent **constant per-step distance penalty equal to `P50(w_cost)`**
- true H3 edge distance should still be retained separately for later route-length, airspeed, and other biological summaries
- distance handling inside the routing cost is now cleaner, but we should still revisit it later if there is a strong scientific reason to depart from the paper formulation

## Dijkstra prototype endpoint decision

The endpoint rule was refined further for the current Svalbard spring prototype.

Updated decision:
- use the Svalbard validation summary file `gdf_SS_10.csv`
- define the prototype start from the **first row** of that file
- define the prototype end from the **last row** of that file
- match those two summary points directly to the nearest H3 cells

Interpretation:
- this is still a prototype endpoint rule rather than a final biological endpoint definition
- but it is cleaner and more defensible than averaging several first/last rows
- it ties the current Dijkstra endpoints directly to the same validation summary object used for Svalbard spring

Chosen mixed behaviors:

Interpretation:

## Full bounded sweep decision

Before RMSE ranking, it was agreed that the project should generate the full candidate route pool under the currently documented bounded coefficient rules.

Current sweep definition:
- `a` wind from 0.0 to 1.0 by 0.1
- `b` crosswind from 0.0 to 0.5 by 0.1
- `c` distance from 0.0 to 1.0 by 0.1
- `d` food from 0.0 to 0.5 by 0.1
- require `a + b + c + d = 1.0`

Important note:
- under these rules the full bounded grid contains **216** behaviors
- this is being treated explicitly as the current project sweep and not automatically as the same thing as the paper's 195-filtered set
- the point of the sweep is to generate the full candidate LCP pool before route-to-benchmark RMSE comparison
